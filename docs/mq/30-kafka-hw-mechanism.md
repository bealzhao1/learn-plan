# Kafka HW（高水位）机制深入解析

## 30.1 什么是 HW 和 LEO

Kafka 的副本同步与数据一致性，核心靠一对概念：**HW（High Watermark，高水位）** 和 **LEO（Log End Offset，日志末端偏移）**。它们是理解 Kafka「消息什么时候才算真正提交、消费者什么时候能读到」的钥匙。

| 概念 | 全称 | 含义 | 谁拥有 |
|------|------|------|--------|
| **LEO** | Log End Offset | 每个副本日志的**末尾偏移**，即「下一条要写入的消息位置」 | 每个副本（Leader 和所有 Follower）各自拥有 |
| **HW** | High Watermark | **高水位**，消费者能读到的最高位置，HW 之前的消息对所有消费者可见 | 整个分区的「提交边界」 |

```
Partition 日志（按 offset 递增）
┌─────────────────────────────────────────────────────┐
│ offset 0 ... 6 │ 7  8  9 │ 10  11  12（仅 Leader 已写）│
│   已提交        │ 已同步但 │ 未同步 / 未提交           │
│  <── HW ──────►│         │                            │
│   消费者可见     │         │                            │
│                └── LEO ──┘  ← Leader 的 LEO            │
└─────────────────────────────────────────────────────┘
         ↑ HW 是「消费者可见」的安全边界
```

**核心公式**：

> **HW = min(所有 ISR 副本的 LEO)**

ISR（In-Sync Replicas）是「和 Leader 保持同步的副本集合」。举例：Leader 的 LEO=10、Follower1 的 LEO=9、Follower2 的 LEO=7，取最小值 → **HW = 7**。

## 30.2 为什么 HW 要取「最小值」

这是理解 HW 的关键。**一条消息只有被所有 ISR 副本都同步了，才算「已提交（committed）」，才对消费者可见。**

沿用上面的例子推演故障场景：

- Leader 虽然已经写到了 offset 10，但 offset 7、8、9 这条消息 Follower2 还没同步到；
- 如果这时 Leader 挂了、Follower2 被选为新 Leader，那 offset 7 之后的数据在新 Leader 上**根本不存在**；
- 如果之前允许消费者读到 offset 9，就会发生「**读到的数据又凭空消失了**」的尴尬。

所以 HW 卡在「最慢的那个副本」的位置，**保证消费者看到的，一定是「即使发生故障切换也不会丢」的数据**。

> HW 的根本意义：它是 **「安全」与「可用」的平衡点** —— 用一点实时性（刚写入的消息要等副本同步才能读），换取「故障切换不丢已提交数据」的强保证。

## 30.3 HW 是怎么计算和传播的

HW 不是静态算一次就完了，而是靠 **Follower 的拉取（Fetch）请求动态维护**的。Kafka 的副本同步是「Follower 主动拉」的模型：

```
        Follower                        Leader
           │                              │
           │  ① Fetch 请求（拉数据 + 上报自己的 LEO）
           │─────────────────────────────►│
           │                              │  ② Leader 汇总所有 ISR 副本的 LEO
           │                              │     计算新 HW = min(各副本 LEO)
           │                              │
           │  ③ 返回数据 + 最新 HW          │
           │◄─────────────────────────────│
           │                              │
           │  ④ Follower 更新自己的 LEO 和 HW │
           │                              │
```

几个关键点：

1. **Follower 是主动方**：周期性地向 Leader 发 Fetch 请求拉取数据，请求里**顺带上报自己的 LEO**。
2. **Leader 是计算方**：Leader 汇总所有 ISR 副本的 LEO，算出新的 `HW = min(LEO)`。
3. **HW 只增不减（单调递增）**：Leader 把新 HW 随响应返回，Follower 也据此更新自己的 HW。
4. **副本进出 ISR** 会直接影响 HW 计算——副本落后太多会被踢出 ISR，此时它不再参与 min 计算，HW 可能因此更快推进。

## 30.4 HW 的三大作用

| 作用 | 说明 |
|------|------|
| **定义「提交」边界** | HW 之前 = committed（已提交），消费者可见；HW 到 LEO 之间 = 已写入但未提交，不可见 |
| **决定消费者可见范围** | 消费者拉取数据时，Leader 只返回 `offset < HW` 的消息，保证读到的一定是「安全」的数据 |
| **保证故障切换不丢数据** | Leader 宕机后，新 Leader 从 ISR 里选出，而 ISR 副本都同步到了 HW 之前的数据，所以**已提交的数据不会丢** |

> 这也解释了 Kafka 的一个常见现象：**刚 produce 的消息，消费者不是立刻就能读到的**——要等所有 ISR 副本同步、HW 推进之后才可见。所以 `acks=all` + 等待 HW 推进，才是「消息确认不丢」的完整含义。

## 30.5 HW 机制的缺陷 → Leader Epoch

HW 这套机制有个著名的问题：**只靠「偏移量」无法区分「是旧 Leader 写的数据」还是「新 Leader 写的数据」**，在特定故障场景（Leader 切换瞬间 + 副本回退）下可能导致**数据丢失**或**数据不一致**。

典型问题场景：

```
旧 Leader A：写了 offset 5（但 Follower B 只同步到 4，A 挂了）
新 Leader B：HW=4，但 B 被选为 Leader 后又写入自己的 offset 5（内容不同）
A 重启后作为 Follower 追平：A 的 offset 5 与 B 的 offset 5 内容冲突
   → 仅靠 offset 对齐，无法判断该保留谁的 offset 5，可能截断错数据
```

于是 Kafka 引入了 **Leader Epoch（纪元）**：

- 给每次 Leader 变更分配一个**递增的纪元号（epoch）**；
- 消息额外记录「在哪个 epoch、哪个 offset 写入的」；
- 切换时，副本带着 epoch 信息对齐数据，能**精确判断哪些数据要截断、哪些要保留**，从根上解决 HW 的边界问题。

所以现在的完整故事是：

> **HW 管「可见性」，Leader Epoch 管「正确性」**，两者配合才真正保证一致。HW 负责告诉消费者「什么能读」，Leader Epoch 负责告诉副本「什么该截断、什么该保留」。

## 30.6 HW / LEO / Leader Epoch 三者关系总结

| 概念 | 管什么 | 一句话 |
|------|--------|--------|
| **LEO** | 每个副本自己的日志末尾 | 「我写到哪了」 |
| **HW** | 分区的提交边界 | 「消费者最多能读到哪」 |
| **Leader Epoch** | 副本数据对齐的正确性 | 「这段数据是谁、在哪个时代写的」 |

## 30.7 面试高频题

| 问题 | 答案要点 |
|------|----------|
| HW 和 LEO 的区别 | LEO 是每个副本自己的末尾；HW 是所有 ISR 副本 LEO 的最小值，是消费者可见边界 |
| 为什么 HW 取最小值 | 保证「已提交」数据一定被所有 ISR 副本同步，故障切换不丢 |
| 消费者为什么读不到刚发的消息 | 消息还没推进到 HW，属于「未提交」 |
| HW 的缺陷 | 只靠 offset 无法区分新旧 Leader 的数据，可能丢数据/不一致 |
| 怎么解决 HW 的缺陷 | Leader Epoch 机制，用纪元号精确对齐，决定截断还是保留 |
| `acks=all` 就等于「不丢消息」吗 | 不是，还要等所有 ISR 同步、HW 推进之后才真正「已提交」 |

## 30.8 一句话总结

> **Kafka 的 HW 机制 =「用所有同步副本 LEO 的最小值，划一条『已提交/可见』的安全水位线」**，让消费者永远只读到「即使 Leader 挂了也不会丢」的数据，代价是牺牲一点实时性。它负责可见性，配合 Leader Epoch 保证正确性，是 Kafka 副本一致性设计的基石。
