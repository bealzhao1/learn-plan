# 消息队列补偿机制

## 29.1 为什么需要补偿

MQ 只保证「消息投递」，不保证「业务最终成功」。当消息丢了、发送失败、消费失败时，必须有一套「兜底机制」把不一致的状态拉回正轨——这就是补偿，目标是**最终一致性**。

补偿分三段：**生产端补偿、消费端补偿、对账兜底**。

## 29.2 生产端补偿：本地消息表方案

核心是第一步的**原子性**：业务数据和消息记录在**同一个本地事务**里落库，从根本上避免「业务成功了但消息没发出去」。

```
┌──────────────────────────────────────────────┐
│  本地事务（原子）                                │
│  1. 写业务数据（如订单表）                        │
│  2. 写消息记录（本地消息表，status=待发送）         │
└──────────────────────────────────────────────┘
                  │ 提交成功
                  ▼
        ┌─────────────────────┐
        │  定时任务扫描          │◄──────┐
        │  status=待发送 的记录  │       │ 失败/超时，
        └─────────┬───────────┘       │ 保持"待发送"
                  │ 投递 MQ             │ 下轮自动重投
                  ▼                     │
           ┌────────────┐              │
           │  投递成功？   │──────────────┘
           └────────────┘
                  │ 成功
                  ▼
          标记 status=已发送
```

- 定时任务（或延迟队列）周期性扫描 `status=待发送` 的记录去投递；
- 投递成功 → 标记「已发送」；
- 投递失败/超时 → **保持「待发送」**，下一轮自动重投。

> 补充：**RocketMQ** 原生支持「事务消息（半消息）」，本质就是这个思路的引擎内置版；**Kafka** 没有事务消息，通常就用本地消息表或 **Outbox 模式**实现。

## 29.3 消费端补偿：重试 → 死信 → 重放

生产端保证了「消息不丢」，但如果消费者**处理业务失败**，光重投消息也没用，需要另一套机制：

```
消费者收到消息
      │
      ▼
 ┌─────────────┐    业务处理失败   ┌──────────────┐
 │  处理业务     │ ───────────────► │  重试（有限次数）│
 └─────────────┘                  └──────┬───────┘
      │ 成功                              │ 超过重试上限
      ▼                                   ▼
  提交 offset                      ┌──────────────┐
   (确认消费)                      │  死信队列 DLQ   │ ← 人工介入/定时重放
                                   └──────────────┘
```

### 三个关键点

**1. 死信队列的真正价值是「隔离」**

如果不把反复失败的消息挪走，它会在主队列里无限重试，**卡住后面所有消息**（尤其 Kafka 单分区内消息是顺序消费的）。丢进死信队列后，主队列继续正常流转，坏消息单独处理。

**2. 幂等是补偿能「重放」的前提**

补偿的本质就是**把同一件事再做一遍**，所以消费逻辑必须幂等——重放 N 次结果一致：

- 唯一键约束（订单号唯一索引，重复插入自动失败但结果正确）；
- 状态机判断（`状态=已处理` 直接跳过）；
- 去重表（Redis SET / 消息 ID 去重）。

> 注意区分：**重试**解决「临时故障」，**补偿**解决「最终一致」，而两者都依赖**幂等**，否则重复消费会造成数据错乱。

**3. 对账是最后一道兜底**

前面所有机制都失效（消息表被误删、DLQ 也处理失败），最终靠**定时对账**把数据拉回一致：比如每天晚上对一遍「订单表 vs 支付流水」，发现「已支付但订单未更新」的记录就主动补一条。

## 29.4 补偿的两个方向（容易忽略）

| 方向 | 含义 | 例子 |
|------|------|------|
| **正向补偿（重做）** | 把没做成的事再做一遍 | 下单成功但扣库存失败 → 补扣库存 |
| **反向补偿（冲正/回滚）** | 把做多了的事撤销 | 扣款成功但下单失败 → 退款冲正 |

分布式事务里常说的 **Saga 模式**，本质就是「每个步骤都配一个反向补偿动作」，一步步回滚。

## 29.5 完整套路总结

```
生产端：本地消息表 + 定时重投  →  保证消息不丢
消费端：重试 + 死信队列 + 幂等重放  →  保证消费最终成功
对账兜底：定时比对  →  保证前两者失效时还能拉回一致
```

核心原则就三条：

1. **最终一致**（不追求强一致）；
2. **幂等**（可安全重放）；
3. **宁可重复不可丢失**。
