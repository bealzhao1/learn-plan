# Kafka 消息堆积排查与治理

## 31.1 堆积的本质

Kafka 消息堆积（Consumer Lag）的根本原因只有一句话：**消费速度追不上生产速度**。

但解决它不能一上来就加机器，得先定位堆积卡在哪一层——是生产端突然暴增、Broker 分区不够，还是消费端处理太慢。三层各对应不同的解法，定位错了，加机器也白加。

```
生产端 ──► Kafka Broker ──► 消费端
   │            │              │
   │            │              └── 消费太慢（最常见）：业务慢 / 串行 / 重试卡死
   │            └── 分区不够：消费者数已到上限，加不动
   └── 突增：大促/秒杀瞬间 QPS 飙升
```

## 31.2 先量化：用命令看 Lag

定位的第一步是**先量化堆积**，用 Kafka 自带的命令查看每个消费者组的 Lag：

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group my-group --describe

# 关注 LAG 列：哪个分区 Lag 持续增长，问题就在哪个分区
```

| 字段 | 含义 |
|------|------|
| CURRENT-OFFSET | 当前消费到的位置 |
| LOG-END-OFFSET | 分区日志末尾（LEO） |
| **LAG** | 两者之差，即积压量，持续增长 = 消费追不上 |

## 31.3 消费者扩容的分区约束（最容易踩的坑）

「加消费者」前必须先搞清楚一个硬约束：**消费者数量不能超过分区数**，超出的消费者会空转。

```
3 个分区，4 个消费者 → 只有 3 个消费者分到分区，第 4 个空转

  P0 ──► C0
  P1 ──► C1
  P2 ──► C2
  (无)    C3  ← 空转，白加

分区数 ≥ 消费者数，加消费者才有意义
```

所以「加消费者」之前，先确认分区数够不够。分区数不够，得先扩分区（见 31.5 的坑）。

## 31.4 堆积原因速查表

| 堆积原因 | 症状 | 对应解法 |
|---------|------|----------|
| 分区数太少，消费者加不动 | 消费者数已等于分区数，Lag 仍涨 | 增加分区数（注意 key 一致性） |
| 单条消息处理太慢（DB 慢/串行） | 消费 QPS 远低于生产 QPS | 优化业务、批量处理、异步化、多线程 |
| 消费失败反复重试 | 某条消息卡住后续所有消息 | 限制重试次数，失败进死信队列（DLQ） |
| 生产端突增（大促/秒杀） | 生产 QPS 瞬间飙升 | 生产端限流、削峰填谷 |
| 消息本身过大 | 网络/序列化开销大 | 消息瘦身、压缩（lz4/zstd） |
| 副本同步慢（Broker 层） | ISR 频繁缩容 | 检查磁盘 IO、扩容 Broker |

> 最后一类要特别强调：**单分区消息是顺序消费的**，如果某条消息处理失败又无限重试，它会**卡住后面所有消息**——这是堆积最常见的「隐形杀手」。所以「失败进死信队列、不阻塞主流程」很关键。

## 31.5 应急止血的手段与代价

应急手段见效快，但都有代价，不能乱用：

| 手段 | 代价 / 风险 |
|------|------------|
| **重置 offset**（跳过积压） | **直接丢弃消息**，只能用于「允许丢」的非核心数据（日志、埋点），核心交易数据严禁 |
| **临时扩分区** | 带 key 的消息会**重新散列**破坏顺序；且分区数**只能增不能减** |
| **扩机器 / 加消费者** | 受分区数约束，分区不够时无效 |

### 临时扩分区到底好不好处理

结论是：**「加消费者」好处理，「扩分区」有代价且基本不是"临时"的**。

| 问题 | 说明 |
|------|------|
| **破坏顺序（最致命）** | 带 key 的消息按 `hash(key) % 分区数` 落区，分区数一变，**同一个 key 的消息会散到不同分区**，原有顺序丢失 |
| **只能增，不能减** | 分区数一旦调大，**缩不回去**，"临时扩一下"是伪命题，扩了基本就是永久的 |
| **改动要提前规划** | 要评估 key 散列变化、消费组 rebalance 影响、磁盘分布 |

**判断标准就一条：这批消息在不在乎 key 的顺序。**

- 消息**无顺序要求**（日志、埋点、无 key）→ 临时扩分区 + 加消费者是**好方案**，成本低见效快。
- 消息**有顺序要求**（订单、交易、带 key）→ 扩分区会破坏顺序，**不能随便扩**，应走消费端优化（见 31.6）。

## 31.6 长期根治方案

长期根治要换思路：**从事后救火，转向「事前预防 + 消费能力建设 + 事后保障」的体系化治理**——让消费能力「结构性」匹配生产能力。

### ① 事前预防 · 把堆积消灭在发生前

1. **分区数倒推规划**：根据历史峰值 QPS 和单消费者实测处理能力反推。`所需消费者数 = 峰值消息速率 / 单消费者处理速率`，分区数 ≥ 消费者数 × 预留系数（2~3 倍）。**分区数只能增不能减，一开始就规划到位**比事后反复扩更划算。
2. **热点分区治理**：key 分布不均会形成「热点分区」——别的分区早消费完，热点分区越积越多。解决：key 加盐、按业务维度重新设计 key，让消息均匀散列。
3. **削峰填谷**：大促/秒杀场景，在生产端就限流 + 本地缓冲，把尖峰摊平，从源头根治。

### ② 事中能力 · 消费端建设（根治核心）

| 手段 | 做法 | 效果 |
|------|------|------|
| **并行化** | 分区级并行（多消费者）+ 分区内多线程 | 直接提升吞吐天花板 |
| **批量处理** | `max.poll.records` 调大，攒批后批量写库 | 减少 DB 交互，吞吐提升数倍 |
| **异步解耦** | 消费线程只负责「快速拉取 + 提交 offset」，业务逻辑丢给线程池/本地队列 | 消费线程不再被慢业务阻塞 |

**关键约束**：分区内多线程处理时，**offset 提交必须保持分区内有序**，否则进程崩溃会导致重复消费或漏消费。正确姿势是「拉取 → 并发处理 → 按原始顺序批量提交」。

**下游保护**：消费慢往往不是 Kafka 慢，而是下游 DB/接口慢。要给下游设**超时 + 熔断降级**，别让一个慢查询拖垮整个消费线程池。

### ③ 事后保障 · 可靠性 + 弹性 + 可观测

1. **可靠消费（不丢 + 不阻塞）**：失败消息「重试 N 次 → 进死信队列」，绝不让一条坏消息卡住整个分区；配合**幂等消费**和**对账兜底**保证最终一致。
2. **弹性伸缩**：消费者跑在容器编排上，**按 Lag 自动 HPA**——Lag 超阈值加消费者（受分区数约束），回落就缩；Broker 侧提前做磁盘 IO、副本数、容量扩容。
3. **可观测 + 分级告警**：监控两个指标——**Lag 绝对值**（超阈值告警）和 **Lag 增长速率**（连续 N 分钟单调上涨，比绝对值更早预警）。

### 落地优先级

| 优先级 | 动作 | 理由 |
|--------|------|------|
| ★★★ | 消费端批量 + 异步化 | 投入小、见效快、无副作用 |
| ★★★ | 失败进死信 + 幂等 | 消除「卡分区」这个最大隐形杀手 |
| ★★☆ | Lag 监控告警 | 可观测是治理的前提 |
| ★★☆ | 分区规划 + 热点治理 | 新建 Topic 时就要做对 |
| ★☆☆ | 弹性伸缩 | 有容器编排基础才划算 |

## 31.7 面试高频题

| 问题 | 答案要点 |
|------|----------|
| 消费者数量为什么受分区数限制 | 一个分区同一时刻只能被组内一个消费者消费，消费者数超过分区数就空转 |
| 为什么不能随便扩分区 | 带 key 消息按分区数取模散列，扩分区后同一 key 会散到不同分区，破坏顺序 |
| 分区数能缩减吗 | 不能，只能增不能减，所以一开始要规划到位 |
| 单分区内为什么一条坏消息会卡住全部 | 分区内是顺序消费的，前面消息不提交，后面的都消费不到 |
| 堆积怎么快速定位 | `kafka-consumer-groups --describe` 看 LAG 列，定位到具体分区 |
| 应急时重置 offset 有什么风险 | 直接丢弃消息，只能用于允许丢的非核心数据 |

## 31.8 一句话总结

> **堆积 = 消费追不上生产**。处理套路是：**先定位（Lag 命令 + 三层排查）→ 再判断能否扩容（消费者数 ≤ 分区数）→ 应急止血（扩分区/重置 offset/扩机器）→ 长期根治（事前规划分区/key/削峰、事中批量+异步+多线程、事后死信+伸缩+监控）**。核心原则两条：**别让"重试失败的消息"卡住整个分区，也别用"丢数据"的应急手段去处理"不能丢"的核心数据。**
