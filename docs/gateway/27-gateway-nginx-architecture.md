# Nginx + 自研网关技术方案（含限流 + 降级）

## 27.1 为什么是「Nginx + 自研网关」两层，而不是二选一

本质是**职责分离**：把「重、无状态、性能敏感」的活交给 Nginx，把「轻、有状态、业务相关」的活交给自研网关。

```
客户端
   │
   ▼
┌─────────────────────────────────────────┐
│  Nginx（边缘接入层）                       │  无状态，可随意扩缩容
│  TLS 卸载 / 静态资源 / WAF / 四层 LB      │  C 实现 + epoll，单机十万级 QPS
└─────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────┐
│  自研网关（业务网关层）                     │  有状态（鉴权、限流计数、灰度标记）
│  鉴权 / 路由 / 灰度 / 限流熔断降级 / 协议转换 │  Go/Java，单机万级 QPS
└─────────────────────────────────────────┘
   │
   ▼
   后端服务集群
```

| 维度 | Nginx（边缘接入层） | 自研网关（业务网关层） |
|------|-------------------|---------------------|
| 定位 | 高性能四层/七层反向代理 | 应用层 API 网关 |
| 有状态性 | 无状态，可随意扩缩容 | 有状态（鉴权、限流计数、灰度标记） |
| 核心能力 | TLS 卸载、静态资源、WAF、四层 LB | 鉴权、路由、灰度、限流熔断降级、协议转换 |
| 性能 | C 实现、epoll，单机十万级 QPS | Go/Java 等，业务逻辑多，单机万级 QPS |
| 扩展性 | 模块 / lua(OpenResty) / 插件 | 自研代码，天然可定制业务逻辑 |
| 为什么需要它 | 承接海量连接、防 DDoS、分担 TLS 计算 | Nginx 无法表达复杂业务规则（按用户/租户限流、按 header 灰度） |

**一句话结论**：Nginx 做「傻快」的通用接入，自研网关做「聪明」的业务治理。流量先过 Nginx 挡掉大部分无效请求，再进网关做精细控制，最后才到后端——**越靠前拦截，成本越低**。

## 27.2 限流方案：三道防线 + 四种算法

限流不是单一动作，而是分层布防：

```
第一道防线：Nginx limit_req / limit_conn
   （无状态，挡掉泛洪攻击、恶意爬虫、单 IP 高频）
        │ 放行的正常流量
        ▼
第二道防线：自研网关分布式限流
   （有状态，按 用户/租户/接口/优先级 精细限流）
        │
        ▼
第三道防线：后端服务本地限流
   （兜底，防止某实例被热点打爆）
```

### 限流算法怎么选

| 算法 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **固定窗口** | 固定时间段内计数，超了就拒 | 实现简单 | 窗口边界「突刺」问题（临界双倍） | 对精度要求不高的场景 |
| **滑动窗口** | 窗口随时间滑动，统计过去 N 秒请求 | 平滑、无突刺 | 实现稍复杂、内存略高 | 网关层通用限流 |
| **令牌桶** | 恒定速率放令牌，请求拿令牌，桶容量=允许突发 | 允许一定突发、平滑 | 突发可能压垮下游 | **Nginx limit_req、网关默认** |
| **漏桶** | 请求进桶、恒定速率流出 | 出流绝对匀速 | 无法应对突发 | 对下游保护要求极严格的场景 |

### 分布式限流关键点

多网关实例时必须解决「单机限流失效」问题（每个实例各自计数）：

- 用 **Redis + Lua 脚本**做原子计数（`INCR` + `EXPIRE` 一条 Lua 保证原子性）。
- 用「滑动窗口 + Redis ZSET」或「令牌桶 + Redis」实现跨实例统一限流。
- 兜底：Redis 挂了时，网关应**降级为本地限流**（放行或本地令牌桶），而不是直接拒绝所有流量。

**限流触达后的动作**：返回 `429 Too Many Requests` + 标准错误体，可选 `Retry-After` 头；对登录/验证码类接口则「限流即熔断」直接拒绝。

## 27.3 降级方案：熔断 + 降级 + 兜底

降级是「下游出问题时，保证核心链路不崩」的最后一道防线。核心是**熔断器（Circuit Breaker）状态机**：

```
        失败率/慢调用 超过阈值
   ┌────────────┐   ──────────────►  ┌────────────┐
   │   Closed    │                    │    Open     │
   │  正常放行    │  ◄──────────────  │  快速失败    │
   └────────────┘      达到熔断时长    └────────────┘
         ▲                               │
         │                               │ 放行少量探测请求
         │     探测成功则关闭             ▼
         │                        ┌────────────┐
         └─────────────────────── │  Half-Open  │
                                   │  半开探测    │
                                   └────────────┘
                                  探测失败则重新 Open
```

### 降级的几种形态

1. **熔断（Circuit Breaking）**：下游错误率/慢调用超过阈值 → 打开熔断 → 快速失败（不再等待超时）→ 半开放探测 → 恢复。关键参数：**错误率阈值**、**最小请求数**（避免小样本误判）、**熔断时长**、**半开探测数量**。

2. **降级（Degradation）**：熔断后不是「裸奔失败」，而是执行兜底逻辑：
   - **兜底数据**：返回缓存的旧数据（如商品详情降级为 Redis 里的快照）；
   - **默认值**：返回空列表 / 默认配置；
   - **只读降级**：写操作降级为返回「稍后重试」；
   - **静默降级**：非核心功能（如推荐位、埋点）直接返回空，不报错。

3. **隔离（Isolation）**：防止某个慢接口拖垮整个网关——线程池隔离（每个下游独立线程池）、信号量隔离（限制并发数）、超时控制（每个下游独立超时时间）。

4. **限流与降级的联动**：限流本身也是降级的一种（保护上游）；当网关自身过载时，可**按优先级**降级——先杀非核心接口（如推荐、活动页），保住核心交易链路。

## 27.4 限流服务出问题了怎么办

限流本来是「保护系统的」，结果它自己成了新的单点故障。核心原则：**限流是「尽力而为」的保护措施，绝不能因为它挂了反而把正常流量挡死。**

### 最关键的设计决策：Fail-Open 还是 Fail-Closed

| 策略 | 行为 | 代价 | 适用场景 |
|------|------|------|----------|
| **Fail-Open（放行）** | 限流失效，流量照常通过 | 可能被瞬时流量打爆下游 | **绝大多数业务接口**（可用性优先） |
| **Fail-Closed（拒绝）** | 限流失效，直接拒绝所有请求 | 正常用户被误杀，可用性暴跌 | **安全敏感接口**（登录防爆破、反爬、验证码） |

**经验法则**：默认 **Fail-Open**。因为「放过一波流量导致下游短时压力」的损失，远小于「把正常用户全挡在外面」的损失——后者是直接的服务不可用事故。

### 六条具体容错措施

1. **本地降级限流（最关键）**：Redis 不可用时，自动切到**进程内令牌桶**（Go 的 `x/time/rate`、Java 的 Guava RateLimiter）。牺牲「多实例全局一致」，保住「单机不被某个实例打爆」。
2. **对 Redis 的调用必须设短超时**：比如 5–10ms。限流是旁路逻辑，绝不能让它拖慢主链路——宁可限流失败，也不能让每个请求都等 Redis 超时 200ms。
3. **限流规则本地快照 + 定时同步**：规则不要每次都从配置中心实时拉，而是定时同步到本地内存。配置中心挂了，网关用本地快照照常工作。
4. **Redis 本身做高可用**：主从 + Sentinel，或 Cluster 集群；可做「本地 + 远程双层」计数。
5. **限流组件也要被熔断**：把「限流依赖」当成普通下游治理，Redis 慢调用超阈值 → 熔断限流调用 → 直接走本地限流。
6. **启动优雅处理**：网关启动瞬间 Redis 还没连上，**不要 panic**，先按本地限流跑，后台异步重连。

### 必须配上的监控告警

- **限流降级次数 / 降级时长**：本地限流被触发的频率，异常升高就告警；
- **Redis 慢查询 / 超时率**：提前发现 Redis 要扛不住了；
- **fail-open 触发次数**：最后的救命稻草，触发就说明前面全挂了，必须立刻告警；
- **限流命中率突降**：突然归零往往意味着限流悄悄失效了。

## 27.5 可直接落地的技术栈建议

| 层 | 选型 | 说明 |
|----|------|------|
| 边缘接入 | Nginx / OpenResty | limit_req 第一道限流，`limit_conn` 限连接，`proxy_cache` 缓存 |
| 业务网关 | 自研（Go，如 go-zero / Kratos 生态 / 手写）+ 参照 Kong/APISIX 插件思路 | Go 高并发适合网关，中间件链式设计 |
| 限流 | 单机：令牌桶（`golang.org/x/time/rate`）；分布式：Redis + Lua | 分维度（IP/用户/接口），分优先级 |
| 熔断降级 | **Sentinel**（有 Go 版）、Hystrix（Java 老牌）、或自研状态机 | Sentinel 支持限流+熔断+降级一体化 |
| 监控 | Prometheus + Grafana，网关打点限流命中率、熔断次数 | 限流/熔断必须可观测 |

## 27.6 最容易踩的三个坑

1. **漏配超时**：网关到下游必须设超时，否则下游慢会拖垮网关线程池 → 引发雪崩。
2. **限流单机化**：多实例部署却用本地计数器，导致限流失效 → 必须分布式。
3. **熔断无兜底**：熔断打开后直接报错，用户体验比慢还差 → 必须有降级逻辑。
